# CyberDefenders Lab: BlackEnergy Writeup

**Category:** Endpoint Forensics | **Difficulty:** Medium  
**Tactic:** Privilege Escalation, Stealth  
**Tools:** Volatility  

**Scenario:**   
A multinational corporation has suffered a cyber attack, resulting in the theft of sensitive data. The attack employed a previously unseen variant of the BlackEnergy v2 malware. The company's security team has obtained a memory dump from the infected machine and is seeking your expertise as a SOC analyst to analyze the dump in order to understand the scope and impact of the attack.

---

### Q1: Which volatility profile would be best for this machine?
*   **Approach:** Extract operating system metadata and hardware architecture from the memory dump to identify the appropriate Volatility analysis profile.
*   **Steps Taken:** 
    *   Executed the `windows.info` plugin: `python3 vol.py -f 99-BlackEnergy.raw windows.info`.
    *   Analyzed the output parameters: `NTBuildLab` indicated `2600.xpsp.080413-2111` (identifying the OS as Windows XP), `CSDVersion` was `3` (Service Pack 3), and `Is64Bit` returned `False` (32-bit x86 architecture).
    *   Although Volatility 3 resolves symbols dynamically without requiring manual profile flags, this lab adheres to Volatility 2 profile naming conventions for 32-bit Windows XP systems.
*   **Evidence:**
    ![Q1 - Volatility Profile Detection](images/q1.png)
*   **Flag:** `WinXPSP2x86`

---

### Q2: How many processes were running when the image was acquired?
*   **Approach:** Enumerate active processes in memory and filter out terminated processes to establish the exact number of running tasks at acquisition time.
*   **Steps Taken:**
    *   Executed the `windows.pslist` plugin: `python3 vol.py -f 99-BlackEnergy.raw windows.pslist`.
    *   Observed a total of 25 process entries traversing the active process list.
    *   Inspected the `ExitTime` column to determine active execution status: 6 processes had terminated prior to acquisition (including `cmd.exe` PID 1960 exiting at `2023-02-13 18:25:26.000000 UTC`, `taskmgr.exe`, `rootkit.exe`, and three `notepad.exe` instances).
    *   Identified 19 processes displaying an `ExitTime` of `N/A`, confirming they were actively executing when the memory dump was taken.
*   **Evidence:**
    ![Q2 - Running Processes List](images/q2.png)
*   **Flag:** `19`

---

### Q3: What is the process ID of cmd.exe?
*   **Approach:** Inspect process listings to identify the unique Process Identifier (PID) assigned to the command prompt executable `cmd.exe`.
*   **Steps Taken:**
    *   Reviewed the process table generated by `windows.pslist`.
    *   Located the specific entry for `cmd.exe`.
    *   Identified that `cmd.exe` was assigned PID 1960 and was spawned by parent process PID 964 (`rootkit.exe`).
*   **Evidence:**
    ![Q3 - Process ID of cmd.exe](images/q3.png)
*   **Flag:** `1960`

---

### Q4: What is the name of the most suspicious process?
*   **Approach:** Analyze the process hierarchy for suspicious naming conventions or anomalies indicative of malicious activity.
*   **Steps Taken:**
    *   Inspected the full process listing generated by `windows.pslist`.
    *   Identified an anomalous executable named `rootkit.exe` running under PID 964 (spawned by `explorer.exe` PID 1484).
    *   A rootkit is a stealth malware category designed to conceal malicious artifacts and maintain elevated privileges, making `rootkit.exe` an overt Indicator of Compromise (IOC).
*   **Evidence:**
    ![Q4 - Suspicious Rootkit Process](images/q4.png)
*   **Flag:** `rootkit.exe`

---

### Q5: Which process shows the highest likelihood of code injection?
*   **Approach:** Scan process memory spaces for abnormal memory protections combined with executable file signatures to detect in-memory code injection.
*   **Steps Taken:**
    *   Executed the memory scanning plugin: `python3 vol.py -f 99-BlackEnergy.raw windows.malfind`.
    *   Discovered that `svchost.exe` (PID 880) contained a private commit allocation (`VadS`) spanning `0x980000` to `0x988fff`.
    *   Observed that this memory segment was granted `PAGE_EXECUTE_READWRITE` permissions, violating standard memory protection policies.
    *   Detected the `4d 5a` (`MZ header`) magic bytes at offset `0x980000`, confirming an injected Windows Portable Executable (PE) payload via Process Injection / Reflective DLL Injection.
*   **Evidence:**
    ![Q5 - Code Injection in svchost.exe](images/q5.png)
*   **Flag:** `svchost.exe`

---

### Q6: There is an odd file referenced in the recent process. Provide the full path of that file.
*   **Approach:** Inspect open object handles belonging to the compromised process (`svchost.exe` PID 880) to detect illegitimate file references.
*   **Steps Taken:**
    *   Executed the `windows.handles` plugin targeting PID 880: `python3 vol.py -f 99-BlackEnergy.raw windows.handles --pid 880`.
    *   Filtered for file objects and identified handle `0x340` referencing `\Device\HarddiskVolume1\WINDOWS\system32\drivers\str.sys`.
    *   Under standard operations, a user-mode service host (`svchost.exe`) does not directly open handles to kernel drivers (`.sys`), and `str.sys` is not a legitimate Windows driver but rather the kernel rootkit component of BlackEnergy.
    *   Converted the kernel device path into a standard drive letter path.
*   **Evidence:**
    ![Q6 - Odd Driver File Handle](images/q6.png)
*   **Flag:** `C:\WINDOWS\system32\drivers\str.sys`

---

### Q7: What is the name of the injected DLL file loaded from the recent process?
*   **Approach:** Detect hidden or unlinked dynamic-link libraries by cross-referencing user-mode PEB structures with kernel-mode VAD memory allocations.
*   **Steps Taken:**
    *   Executed the `windows.ldrmodules` plugin for PID 880: `python3 vol.py -f 99-BlackEnergy.raw windows.ldrmodules --pid 880`.
    *   Inspected the three PEB module tracking lists: `InLoad` (load order), `InInit` (initialization order), and `InMem` (memory address order).
    *   Identified module `\WINDOWS\system32\msxml3r.dll` mapped at base address `0x9a0000`, which returned `False False False` across all three tracking lists.
    *   This confirms the malware employed the PEB Unlinking technique to hide `msxml3r.dll` from standard inspection tools and `windows.dlllist` while keeping the binary code executable in RAM.
*   **Evidence:**
    ![Q7 - Hidden DLL msxml3r.dll](images/q7.png)
*   **Flag:** `msxml3r.dll`

---

### Q8: What is the base address of the injected DLL?
*   **Approach:** Determine the base virtual memory address where the injected malicious module payload begins execution inside PID 880 as identified by `malfind`.
*   **Steps Taken:**
    *   Reviewed the suspicious memory segment detected by `windows.malfind` in PID 880: `python3 vol.py -f 99-BlackEnergy.raw windows.malfind --pid 880`.
    *   Located the private memory region (`VadS`) with `PAGE_EXECUTE_READWRITE` permissions spanning `0x980000` to `0x988fff`.
    *   Verified that the starting offset `0x980000` contains the `4d 5a` (`MZ header`) signature, representing the base address of the injected PE payload.
    *   Extracted the `Start VPN` address `0x980000` as evaluated by the CyberDefenders scoring criteria.
*   **Evidence:**
    ![Q8 - Injected Module Base Address](images/q8.png)
*   **Flag:** `0x980000`
